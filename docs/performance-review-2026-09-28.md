# UndoTree 性能検証（2026-09-28）

この文書は改善前の測定記録。改善内容と再測定は [性能改善の検証結果](performance-improvements-2026-09-28.md) を参照。

大きなファイルと大量の履歴を組み合わせると、性能・表示の問題がある。優先度が高いのは、深い履歴の描画停止と Hard Compact プレビューの同期処理による長時間停止。その次に、差分チェーン復元と全文スナップショットの保持・画面転送を改善する必要がある。

## 測定条件

- 対象: `f6966c7` を基にした作業ツリー。前回の保存・一時停止・リネーム修正を含む。
- Windows、Intel Core i5-13400F、Node.js 22.22.0。
- 実機: VS Code 1.136.0 の Extension Development Host。独立した一時プロファイルを使用。
- 表示処理単体: Edge 154.0.4258.37 の headless Chromium、340 × 900 px。実装が生成した Webview HTML をそのまま使用し、`acquireVsCodeApi` のみスタブ化。
- 1 MiB = 1,048,576 bytes。ファイルは約63文字ごとに改行する繰り返しASCIIテキスト。
- 差分ケース: ファイル中央に短い文字列を挿入して保存。件数は初期ノードを除く。10,000回保存なら10,001ノード。
- 全文ケース: 1 MiBの内容を変えて100回保存。差分バッファを渡さず、毎回 `full` ノードになる条件。
- 単体測定はケースごとに別Nodeプロセス。メモリは明示的GC後のヒープ増分。履歴データと現在の文書文字列を含み、エディター本体やWebviewのメモリを含まない。
- 実機は保存済み履歴をロードして測定。設定は `persistenceMode=manual`、`autosaveInterval=0`。Undo/Redoは実際の拡張コマンドを実行。
- 10 ms間隔のタイマーの遅延から、拡張ホストのイベントループ停止時間を測定。

繰り返しテキストは圧縮率が非常に高い。永続化時間は圧縮しにくい実データの上限を示すものではない。単発測定や少数回の測定を含み、環境間の保証値ではない。

## 実際のVS Codeでの測定

| 初期サイズ / 履歴 | 開くAPIの所要時間 | Undo | Redo | Undo/Redo中の最大イベントループ遅延 |
| --- | ---: | ---: | ---: | ---: |
| 1 MiB / 1,000差分 | 360 ms | 198 ms | 195 ms | 138 ms |
| 10 MiB / 500差分 | 1,513 ms | 1,792 ms | 3,406 ms | 1,350 ms |
| 20 MiB / 100差分 | 955 ms | 1,083 ms | 1,554 ms | 822 ms |
| 1 KiB / 10,000差分 | 205 ms | 69 ms | 66 ms | 35 ms |
| 1 MiB / 100全文 | 128 ms | 59 ms | 49 ms | 11 ms |

「開く」は `openTextDocument` + `showTextDocument` の完了時間。サイドバー描画完了を含む保証はない。10,000差分のコマンド処理が速くても、後述の表示停止は別途発生する。

全文100件は永続化済みなので、大きな全文ノードがcheckpointとして遅延ロードされる。編集中に全文ノードが積み上がった場合とは条件が異なる。

50 MiBに挿入を加えたファイルは、このVS Codeで `Files above 50MB cannot be synchronized with extensions` によりAPIから開けなかった。以下の50 MiBの数値はマネージャー単体の結果であり、実機でこのサイズを追跡できたことを意味しない。

実機の拡張ホストヒープは途中で約779 MiBまで上昇したが、ケースを連続実行し、GCを強制していないため、特定ケースの保持量やメモリリークの証拠として扱わない。

## 指摘と改善優先度

### P1: 深い履歴が再帰上限で表示できなくなる

`src/undoTreeProvider.ts` の `renderNode` は子ノードを再帰呼び出しする。10,001ノードの直列履歴を実装のHTMLで表示したところ、2,032ノードで `RangeError: Maximum call stack size exceeded` が発生した。最後の履歴まで描画されず、現在位置やキーボード操作の初期化まで到達しない。

再帰を明示的なスタックによる走査に変更する必要がある。そのうえで、全件DOM再作成を避ける表示の仮想化または段階的な描画を検討する。2,032という境界値は今回のブラウザー環境に依存する。

### P1: Hard Compactプレビューが履歴数の二乗に近い仕事を繰り返す

`src/undoTreeManager.ts` の `previewHardCompactDetailed` は、各保護ノードについて `getHardCompactProtectReason` を呼ぶ。そのたびに最新ノード探索、現在位置と最新位置の祖先集合、注釈・ピン付き祖先集合を計算し直す。

10,001ノードではプレビュー生成単体が約23秒。`src/extension.ts` のプレビュー表示から同期呼び出しされるため、実行中は拡張ホストのほかの仕事を進められない構造になっている。実機で23秒を測ったのではなく、同じ関数の単体測定と呼び出し経路による判定。

保護判定に必要な集合をプレビュー全体で一度だけ作成し、各ノードで再利用する。

### P2: 大きなファイルの長い差分チェーンで復元が重い

`reconstructContent` / `reconstructContentAsync` は基準の全文ノードまで遡って、全文文字列に差分を順番に適用する。中央への編集では文字列を繰り返し生成する。現在の保存処理では分岐点の昇格はあるが、直列チェーンの長さを制限する定期checkpointはない。

10 MiB・500差分は単体でも約1.2秒、実機ではUndo約1.8秒・Redo約3.4秒。UIへの文書反映も含む実機時間と、復元関数だけの時間は区別する必要がある。実機で約1.35秒の拡張ホスト停止も確認した。

差分数または累積編集量で復元コストを制限するcheckpoint、直近復元結果の再利用、長い処理での実行権の解放を検討する。`path.unshift` による配列先頭挿入も `push` + 反転で避けられるが、全文文字列の再構成コストの解決にはそれだけでは足りない。

### P2: 表示に不要な本文と差分をWebviewへ送っている

`src/undoTreeProvider.ts` の `getRenderState` は `...node` を展開するため、`storage.content` と `storage.diffs` までHTMLや更新メッセージに含まれる。ブラウザー側の表示が使うのは保存形式の種類やメタデータであり、本文そのものは不要。

1 MiBの全文100件で表示用JSONは約103 MiB。サイズと保存回数に応じて、不要なシリアライズ・転送・ブラウザー側のメモリ保持が増える。表示専用DTOを用意し、保存形式は `kind` のみにする改善が有効。

### P2: 全文履歴にはキャッシュ設定とは別にメモリが積み上がる

`UndoNode.storage.kind === 'full'` の文字列はツリー内に保持される。`contentCacheMaxKB` はcheckpointの内容キャッシュを制限する設定であり、これら全文ノードや差分バッファ全体を制限しない。

1 MiB × 100全文ではGC後も約101 MiBを保持した。永続化時のcheckpoint化は出力側の変換なので、保存だけでresident treeの全文文字列が解放されるわけではない。

永続化済み全文の参照化、履歴全体の予算設定、長時間編集・大量置換時の差分バッファの扱いを検討する。未永続化の唯一のコピーを捨てる変更は避け、履歴の復元可能性を維持する必要がある。

## 確認できた範囲と残る範囲

- 既存性能テスト36件はすべて成功。ただし、大量履歴のWebview描画や、10,000件のHard Compact詳細プレビューをカバーしていない。
- 差分保存自体のCPU時間と、差分形式の保持メモリは比較的小さい。保存が速いことだけで、表示・復元も速いとは判断できない。
- 実機で50 MiB超は拡張APIの制限を確認。20 MiBは測定できた。
- 多数ファイルを同時に保持するケース、巨大な未保存差分、実用データの圧縮率、長時間のメモリ推移、ネットワークファイル・Remote環境は未測定。
- 今回は性能調査。アプリ本体の性能改善は行っていない。
