# 性能改善の検証結果（2026-09-28）

大容量ファイルの差分復元、大量履歴の描画・整理プレビュー、全文スナップショットの保持を改善した。履歴を間引くことなく、既存の保存形式を引き続き読み込める。

## 同じ条件での比較

測定環境・データ生成条件は [改善前のレポート](performance-review-2026-09-28.md) と同じ。以下は管理処理と生成したWebview HTMLの測定であり、VS Code全体の所要時間ではない。

| 対象 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 1 MiB / 1,000差分の同期復元 | 316 ms | 10.3 ms |
| 10 MiB / 500差分の同期復元 | 1,246 ms | 7.0 ms |
| 20 MiB / 100差分の同期復元 | 434 ms | 4.3 ms |
| 50 MiB / 100差分の同期復元（管理処理のみ） | 1,082 ms | 9.2 ms |
| 10,001ノードのHard Compactプレビュー | 22,977 ms | 23 ms |
| 10,001ノードの表示 | 約2,032行で再帰上限エラー | 全履歴に移動可能、DOMは81行 |
| 10,001ノードの再描画 | エラーのため測定不可 | 10.5〜12.7 ms |
| 1,001ノードの再描画 | 79〜94 ms | 10.1〜13.0 ms |
| 1 MiB / 100全文の表示用JSON | 102.63 MiB | 0.019 MiB |
| 同・初回HTML読込 | 1,393 ms | 99 ms |
| 同・本文の保持量 | 全文101 MiB | 全文2 MiB + 圧縮バッファ1.26 MiB |

本文保持量は、ノード内の全文のUTF-8バイト数と圧縮バッファの実バイト数を数えた値。プロセス全体のメモリ使用量ではない。改善前のGC後ヒープ増分は101.1 MiBだったが、再測定ではTypeScript変換器などのGCタイミングによる揺れ・負値があり、ヒープ増分をメモリ削減率の根拠には使っていない。文書本体、メタデータ、解凍キャッシュ、作業バッファは別途必要になる。

全文ケースは圧縮率の高い繰り返しテキスト。圧縮しにくいデータではこの保持量にはならない。1 MiB全文の保存P50は1.46 msから3.13 ms、P95は2.31 msから4.38 msになり、圧縮のCPUコストとの交換になる。より大きなスナップショットは非同期圧縮とし、待機中も全文を保持する。圧縮の完了前に保存やリセットが起きても履歴を失わない。

## 実装内容

- Webviewに送るデータを表示用メタデータだけに限定。本文・差分・ハッシュは送らない。
- ツリーを明示的なスタックで走査。500ノードを超える場合は表示領域とその前後だけを描画する。全ノードの順序とIDは保持し、Home/End・上下キー・ピン留めからの移動に対応する。
- 整理プレビューの祖先集合と最新ノード探索を一度だけ計算して再利用。
- 大容量テキストの差分は文字列の断片としてまとめて適用し、最後に結合。各編集で全文をコピーしない。断片が増えすぎた場合はまとめ直して探索量を制限する。
- 復元経路の先頭挿入と、行数取得のための全文splitを廃止。
- 大容量ファイルへのUndo/Redo適用では、共通の前後部分を残し、変更範囲だけをエディターに送る。全文置換によるエディター側の再処理を避ける。置換範囲はCRLFやサロゲートペアの途中で区切らない。
- 256 Ki文字以上の古い全文ノードを、設定されたメモリcheckpoint閾値に従って圧縮。ルートと現在のスナップショットはこの変換の対象外。1 Mi文字を超える圧縮は一つずつ非同期実行する。UTF-16コード単位を保持し、日本語・絵文字・孤立サロゲートもメモリ内で往復できる。
- 保存の完了確認まで圧縮バッファを保持。本文キャッシュの上限を超える解凍結果はキャッシュしない。小さい未保存checkpointの唯一のコピーは引き続き保護する。
- 永続化時に同時に展開・圧縮する本文を4件までに制限。各ツリーを順番に保存し、開始した書込みが完了するまでストレージのロックを保持する。
- 既存checkpointと小さな全文ノードが混在すると、実際には書き出していない本文ファイルへの参照を保存する不具合も修正。書き出す対象の全文だけをcheckpoint形式に変換する。

## 検証

- 単体・永続化統合テスト: 228件。
- 既存の性能テスト: 36件。
- 生成HTMLをEdgeで実行: 6条件すべて。全履歴のID保持、DOM数上限、Home/End・上下移動・Enter、スクロール、ピン留め、ペア差分、分岐順序、非ゼロのルートIDを検証。
- ランダムな3,200編集、複数カーソルの変更、UTF-16境界、全消去後の挿入を逐次適用の参照実装と比較。
- キャッシュ上限0、非同期圧縮中のリセット、古い保存世代の完了、複数ファイルで共有するcheckpoint、永続化後の全スナップショット復元を検証。

## 実際のVS Codeでの比較

VS Code 1.136.0の独立したプロファイルで保存済み履歴を開き、拡張のUndo/Redoコマンドを実行。Undoで内容が変化し、Redoで元の全文に一致することを毎回assertした。APIの完了時間であり、単体の復元時間とは異なる。

| 条件 | Undo 改善前 → 後 | Redo 改善前 → 後 | 操作中の最大イベントループ遅延 改善前 → 後 |
| --- | ---: | ---: | ---: |
| 1 MiB / 1,000差分 | 198 → 20 ms | 195 → 8 ms | 138 → 7 ms |
| 10 MiB / 500差分 | 1,792 → 27 ms | 3,406 → 14 ms | 1,350 → 9 ms |
| 20 MiB / 100差分 | 1,083 → 37 ms | 1,554 → 16 ms | 822 → 17 ms |
| 1 KiB / 10,000差分 | 69 → 60 ms | 66 → 49 ms | 35 → 28 ms |
| 1 MiB / 100全文 | 59 → 16 ms | 49 → 4 ms | 11 → 10 ms |

実機の1万件のサイドバーでも現在位置・先頭/末尾へのキーボード移動を確認。高さ180 pxの小さいサイドバーは生成HTMLのテストでも確認し、フォーカスした行が固定ツールバーに隠れないようにした。

最初にファイルを開く処理にはまだ数百msかかる。今回の10 MiBは796 ms、20 MiBは677 msで、読込・表示中の最大タイマー遅延はそれぞれ445 ms・787 msだった。この測定だけでVS Code本体と拡張の内訳は確定できない。拡張ホストのヒープ値も連続ケース間でGCのタイミングが揺れるため、メモリリークがないことの証明には使っていない。

実機の回帰テスト9件もすべて成功。保存、一時停止・再開、整理、フォルダーのリネーム、外部変更、キャッシュ上限0での全文履歴、再起動後の復元を対象とする。

改善前の実装で保存した測定用履歴も、最終版のVS Code実機で再読込してUndo/Redoの内容一致を確認した。開ける5条件は成功し、50 MiB超の条件だけが既知のVS Code同期上限で対象外だった。

生データは [改善後の測定JSON](performance-improvements-results-2026-09-28.json)、改善前は [元の測定JSON](performance-results-2026-09-28.json) に保存。

## 再現

```powershell
npm test -- --runInBand
npm run test:perf -- --runInBand
npm run package
node scripts/benchmark-history.cjs
node scripts/benchmark-history-renderer.cjs <上記の出力ディレクトリ>
node scripts/benchmark-vscode-history.mjs <上記の出力ディレクトリ>
node scripts/run-vscode-history.mjs
```

実機スクリプトはインストール済みVS Codeを独立した一時プロファイルで起動する。50 MiBに挿入を加えたファイルは、今回のVS Codeでは拡張APIとの同期上限により開けない。この制限は変更していない。
